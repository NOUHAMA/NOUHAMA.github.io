Data Pipeline Project

This project presents an end-to-end analytics pipeline built around SQL, Snowflake, and dbt. The workflow covers raw data ingestion, staging, testing, documentation, snapshotting, and transformation into analysis-ready models for reporting and decision-making.

Data Model & Architecture

The following diagram represents the structure of the data warehouse, including fact and dimension tables. The model follows a star schema design, where the central FACT_SALES table is connected to multiple dimension tables such as customer, product, geography, and time-related data.

This structure enables efficient querying and supports analytical use cases such as sales performance, customer segmentation, and geographic analysis.

Pipeline Overview

This project was developed using a dataset imported from Kaggle and processed through a modern data workflow. Raw data was loaded into Snowflake, structured with dbt, validated using tests, and transformed into clean analytical models. The objective was to create a reliable and maintainable pipeline that supports data quality, traceability, and efficient reporting.

Tools Used

SQL Snowflake dbt YAML Data Modeling Testing Snapshots

Project Workflow

  • Data Source: Imported a business dataset from Kaggle.
  • Storage Layer: Loaded raw data into Snowflake tables.
  • Transformation Layer: Organized models with dbt into staging, intermediate, and marts layers.
  • Quality Control: Added source tests such as unique and not_null to validate key fields.
  • Documentation: Defined metadata in YAML files for sources, models, and columns.
  • Historical Tracking: Used snapshots with a timestamp strategy to capture changes in fact data over time.

dbt Project Configuration

The dbt project was structured to separate models into clear layers: staging, intermediate, and marts. This organization improves readability, maintenance, and scalability. 

name: my_analytics
version: "1.0.0"
config-version: 2

profile: analytics

model-paths: ["models"]

models:
  my_analytics:
    staging:
      +materialized: view
      +schema: staging
    intermediate:
      +materialized: view
      +schema: intermediate
    marts:
      +materialized: table
      +schema: marts

Source Definition and Data Quality

Source metadata was defined in source.yml to describe the raw Snowflake tables and apply tests on critical columns. Primary identifiers such as CATEGORY_ID, PRODUCT_ID, CUSTOMER_ID, and ORDER_KEY were validated with unique and not_null checks. Freshness rules were also configured on the fact table to monitor data recency. 

version: 2

sources:
  - name: superstore
    database: ecommerce_project
    schema: raw
    tables:
      - name: CATEGORY_DIM
        columns:
          - name: CATEGORY_ID
            tests:
              - unique
              - not_null

Model Properties and Documentation

Model metadata was documented in property.yml to describe the staging models and define the meaning of important columns. This helps make the project easier to understand, improves collaboration, and keeps the transformation logic well documented for future use.

  • Documented fact and dimension models

Snapshots for Change Tracking

A snapshot was configured on the FACT_SALES table using a timestamp strategy. This allows the pipeline to preserve historical changes and track updates over time instead of only keeping the latest version of the data. This is especially useful for analytical consistency and auditability. 

snapshots:
  - name: fact_sales_snapshot
    relation: source('superstore', 'FACT_SALES')
    config:
      unique_key: SALES_KEY
      strategy: timestamp
      updated_at: updated_at
